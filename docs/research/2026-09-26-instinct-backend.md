# AMD Instinct backend for zerv: research note and dependency-boundary proposal — 2026-09-26

**Question.** How can zerv run on AMD Instinct GPUs (MI300X/MI325X: CDNA3, `gfx942`;
MI355X: CDNA4, `gfx950`)? The engine has to stay from-scratch Zig with no C++ dependency
([AGENTS.md](../../AGENTS.md)). What exactly has to be built, what can we reuse, and which
dependency-boundary change needs approval? Context: [rented GPUs](2026-09-26-rented-gpu-economics.md),
[bigger models](2026-09-26-bigger-models.md). The user's direction is AMD-first.

**Status.** Research only. No code, nothing rented, no contact.

revisions and SHA-256 is [sources.json](2026-09-26-instinct/sources.json):

## Recommendation

1. **Talk to the kernel's KFD interface directly from Zig, and use no ROCm userspace** [P].
   - The runtime needs: `open`, `ioctl` and `mmap` on `/dev/kfd` and the DRM render node;
     sysfs topology reads; AQL queues; and our own loader for our own code objects.
   - This is the same class of system interface as the Vulkan loader and RADV we use today.
     No HIP, ROCr, libhsakmt, comgr, hipBLASLt or RCCL. All of these are C++ (or wrap C++)
     and forbidden by AGENTS.md.
2. **GPU code: our generators emit AMDGPU assembly, assembled offline** [P].
   - The assembler is LLVM's (`clang`/`llvm-mc`), used as a development tool. The machine
     code is checked in with hashes, never compiled at build or run time.
   - **This is the precedent we already have**: the RDNA3 `gemm_f16x` kernel ships as our
     own machine code, generated by `bench/isa_lab/gen_f16x.py` and assembled by clang
     ([development.md](../development.md#native-machine-code-srcmodelnative),
     [report](../bench/2026-09-24-gemm-f16x-isa.md)).
   - A later option is our own encoder, which would remove LLVM even as a tool. tinygrad
     has one: CDNA instruction encodings, an AMD assembly DSL and an ELF writer [S].
3. **Build the runtime locally before renting anything** [O].
   - This machine exposes `/dev/kfd` (mode 0666). KFD node 1 is the RX 7900 XTX:
     `gfx_target_version` 110000, 192 SIMDs, wave32, 64 KiB LDS, `cwsr_size` 46,047,232,
     `ctl_stack_size` 40,960, 8 CP queues, 2 SDMA engines, one XCC.
   - Memory, queues, signals, code-object loading and dispatch are the same mechanism on
     Instinct. Only the ISA-specific kernels and multi-XCD details need rented hardware.
4. **Vulkan on Instinct is not the plan.** Whether RADV exposes a compute-only `gfx942`
   device is unverified. The installed `libvulkan_radeon.so` (Mesa 26.2.3) contains the
   strings `GFX940`/`gfx942` and "device '%s' is not supported by RADV" [O]. Whether its
   compiler (ACO) emits the matrix instructions (MFMA) is also unknown. A `vulkaninfo`
   check on the first rented MI300X settles it cheaply. Even if it worked, the matrix
   pipes would run under a driver compiler we don't control.
5. **Prior art showing this is feasible** [S]:
   - tinygrad's `ops_amd.py` drives AMD GPUs through `/dev/kfd` ioctls with its own queues.
     It uses AQL queues when a device has more than one XCC (MI300X), PM4 queues otherwise.
   - It sizes each queue's context-save area from topology (`cwsr_size`, `ctl_stack_size`),
     calls `AMDKFD_IOC_RUNTIME_ENABLE` on KFD ≥ 1.14, and maps the doorbell page from
     `/dev/kfd`.
   - It sets up architected flat scratch per XCC.
   - We read it as research only (MIT), and nothing is copied.

## 1. Hardware [S unless marked]

| | MI300X / MI325X (CDNA3) | MI355X (CDNA4) | RX 7900 XTX (ours, RDNA3) |
| --- | --- | --- | --- |
| LLVM target | `gfx942` (sramecc, tgsplit, architected flat scratch) | `gfx950` (same features) | `gfx1100` |
| Compute units | 304 over 8 XCDs | 256 over 8 XCDs (32 active of 36 per XCD) | 96 [O] |
| Wave size | 64 | 64 | 32 or 64 |
| Peak clock | 2,100 MHz | 2,400 MHz | ~2.5–2.9 GHz measured [O] |
| LDS per CU | 64 KiB | **160 KiB**, 2× read bandwidth, can load straight from L1 | 64 KiB |
| L1 / L2 | 32 KiB per CU / 4 MB per XCD | 32 KiB / 4 MB per XCD | – |
| Infinity Cache (memory-side) | 256 MB | 256 MB | 96 MB |
| HBM | 192 GB HBM3, 5.3 TB/s (MI325X: 256 GB HBM3E, 6 TB/s) | 288 GB HBM3E, 8 TB/s | 24 GB GDDR6, ~0.96 TB/s |
| Dense matrix throughput, FLOPs/clock/CU | FP16/BF16 2,048; FP8 4,096 | FP16/BF16 4,096; FP8 8,192; MXFP6/MXFP4 16,384 | – |
| Dense peaks | BF16 1.3 PF, FP8 2.6 PF | BF16 2.5 PF, FP8 5.0 PF, MXFP4 10 PF | f16 WMMA ~135 TF measured [O] |
| FP8 E4M3 encoding | FNUZ-style: max 240, one NaN (0x80), no ±0 distinction | OCP: max 448 | – |
| Scale-up | 7 × 16 Infinity Fabric links (xGMI) per GPU, 8-GPU nodes | 7 × 16 links, >1 TB/s per GPU, 8-GPU nodes | – |

**Matrix instructions** (CDNA3 ISA Table 28, CDNA4 equivalent):
- **CDNA3 (MI300X/MI325X).** `V_MFMA_F32_{16x16x16, 32x32x8}_{F16,BF16}` at 16/32 cycles.
  `V_MFMA_F32_{16x16x32, 32x32x16}_{FP8,BF8 combos}` at 16/32 cycles. `I8` 16x16x32 and
  32x32x16. XF32 and F64 variants.
- **CDNA4 (MI355X) adds:**
  - `F16/BF16 16x16x32, 32x32x16`;
  - `I8 16x16x64, 32x32x32`;
  - `V_MFMA_F32_{16x16x128, 32x32x64}_F8F6F4`, with the A and B formats chosen
    independently;
  - `V_MFMA_SCALE_F32_*_F8F6F4` with block scales (the MX formats);
  - `V_CVT_SCALEF32_*` conversion instructions.
- **Rules for all MFMA:**
  - rounding is forced to round-to-nearest-even;
  - input and output denormals are kept;
  - the exec mask is ignored (forced to 1);
  - VGPR operands must be even-aligned.
- **The FP32 accumulation order and exactness are not documented at the level zerv's
  batch-invariance gates need.** An exactness probe is required, like the one we ran for
  RDNA3 WMMA ([coopmat research](../bench/2026-09-23-coopmat-research.md), which found f16
  WMMA accumulation is not IEEE).

**Memory model (gfx942; gfx950 uses the same cache bits)** [S, AMDGPUUsage]:
- **L2 is per XCD.** It stays coherent with other L2s only through MTYPE NC plus the PTE
  C-bit for non-local memory.
- **Agent-scope release/acquire** needs `buffer_wbl2` / `buffer_inv sc1`. Loads and stores
  carry `sc0`/`sc1`/`nt` bits.
- **Consequence:** kernels should avoid communicating between workgroups across XCDs
  (split-K reductions, atomics). Where they must, they pay agent-scope fences.
- **Dispatch spreads workgroups over all XCDs**, and a tile's XCD decides which L2 caches
  it. XCD-aware tile ordering is a known optimization; measure it.
- **Partitioning.** The GPU can be set up as several smaller agents (CPX/SPX compute
  partitions, NPS memory modes). What a rented VM exposes is a provider setting, still to
  observe.

## 2. Software interface [S]

**Topology:**
- Each node in `/sys/devices/virtual/kfd/kfd/topology/nodes/N/properties` lists:
  `gfx_target_version`, `simd_count`, `cu_per_simd_array`, `max_waves_per_simd`,
  `lds_size_in_kb`, `wave_front_size`, `num_xcc`, `cwsr_size`, `ctl_stack_size`,
  `drm_render_minor`, `local_mem_size`, `num_sdma_engines`, `num_sdma_xgmi_engines`,
  `num_cp_queues`, `hive_id`, `capability`, and more.
- `io_links` describe the xGMI/PCIe peers.

**KFD ioctls** (ABI 1.23 in Linux 7.2), the subset we need:

| ioctl | Use |
| --- | --- |
| `GET_VERSION` | ABI check (≥ 1.14 for `RUNTIME_ENABLE`) |
| `ACQUIRE_VM` (with the render-node fd) | bind the process to the GPU VM |
| `GET_PROCESS_APERTURES_NEW` | GPUVM, LDS and scratch apertures |
| `ALLOC_MEMORY_OF_GPU` (VRAM / GTT / USERPTR / DOORBELL; WRITABLE, EXECUTABLE, PUBLIC, COHERENT, UNCACHED, NO_SUBSTITUTE, CONTIGUOUS) + `MAP_MEMORY_TO_GPU` / `UNMAP` / `FREE` | memory: device-local weights, host-visible I/O, peer maps via several `gpu_id`s |
| `AVAILABLE_MEMORY` | budget checks (our Vulkan-side `--vram-reserve` equivalent) |
| `CREATE_QUEUE` (`COMPUTE_AQL`; ring, read/write pointers, EOP buffer, context-save area of `cwsr_size`, control stack of `ctl_stack_size`, times `num_xcc`) / `DESTROY_QUEUE` | compute queues; `SDMA` and `SDMA_XGMI` queue types for copies |
| `CREATE_EVENT` / `WAIT_EVENTS` / `DESTROY_EVENT` | completion interrupts; the alternative is polling signal memory |
| `RUNTIME_ENABLE` | required by current runtimes for context save/restore and debugger compatibility |
| `SET_XNACK_MODE`, `SET_MEMORY_POLICY`, `SVM` | optional; we allocate explicitly and want no page faults |

**AQL (HSA packet processor):**
- The ring holds 64-byte packets. A kernel dispatch packet carries: setup dimensions,
  workgroup size, grid size, private and group segment sizes, `kernel_object` (the
  address of the 64-byte kernel descriptor), `kernarg_address` and `completion_signal`.
  Barrier-AND/OR packets order work.
- The packet header is written last with release ordering; then the doorbell is rung with
  the write index.
- The queue memory follows `amd_queue_t` (`amd_hsa_queue.h`: `write_dispatch_id`,
  `read_dispatch_id`, scratch fields; v2 extensions only when the caps bit is set).

**Code objects:**
- AMDGPU ELF: `EM_AMDGPU`, `e_flags` carrying `gfx942`/`gfx950` plus the
  sramecc/xnack settings.
- The kernel descriptor symbol (`<name>.kd`, 64 bytes, 64-byte aligned) holds the group
  and private segment sizes, the kernarg size, the entry offset and
  `compute_pgm_rsrc1/2/3`.
- `gfx942`/`gfx950` use *architected flat scratch*: no private segment buffer, and the
  queue holds the scratch setup.
- The msgpack metadata note is consumed by ROCr, not the CP. Our loader can use our own
  checked metadata but should still emit a standard ELF, so that `llvm-objdump` and
  `readelf` can inspect it.

**Header use:**
- We do not import C headers. The uapi structures become Zig `extern struct`s, with
  compile-time size and offset assertions.
- Reference values come from a development script that reads the pinned uapi header.
  `kfd_ioctl.h` is GPL-2.0 WITH Linux-syscall-note, the standard uapi exception.

## 3. Dependency-boundary proposal (needs your approval) [P]

| Layer | Allowed | Not allowed |
| --- | --- | --- |
| Runtime (native binary) | Linux uapi: `open`/`ioctl`/`mmap` on `/dev/kfd` and `/dev/dri/renderD*`, sysfs reads; Zig std; our code objects embedded or loaded from checked files | libhsakmt, ROCr, HIP, comgr, libdrm_amdgpu, rocBLAS/hipBLASLt, RCCL, MIOpen, any ROCm userspace |
| Development tools (never linked; outputs checked in with hashes) | LLVM `clang` / `llvm-mc` (AMDGPU assembler), `llvm-objdump` for disassembly checks; our Python/Zig generators | compiling at build or run time; LLVM IR / HIP kernels as the source of shipped code |
| Oracles and competitors (external, on rented machines) | ROCm, vLLM, SGLang, ATOM, rocm-bandwidth-test, hipBLASLt benchmarks, transformers on CPU for model fixtures | using their outputs as anything but fixtures and benchmarks |

**If approved:** record this in [development.md](../development.md), next to the Vulkan
boundary, and pin the LLVM version used to assemble. Until then, nothing in `src/` changes.

## 4. Verification plan (before any kernel counts)

1. **Host layer.** Zig structs match the uapi: sizes and offsets checked against values the
   development script extracts from the pinned header. Topology parsing is tested on saved
   sysfs snapshots (this machine's, and a rented MI300X's).
2. **Device bring-up, locally on `gfx1100`:**
   - allocate, map, fill and copy with our own kernels;
   - AQL barrier ordering; completion through signals and events;
   - negative tests: bad VA, unmap while busy, queue destroy with pending packets, OOM,
     ring wrap;
   - bounded waits with timeouts; no leaked BOs (checked through `AVAILABLE_MEMORY`).
3. **Differential results against the Vulkan path on the same card.** The same algorithm
   (e.g. Q4_0 matvec) is run through Vulkan (RADV-compiled) and through KFD
   (our assembly). The outputs are compared with each kernel's declared exactness contract.
4. **Instinct hardware:**
   - MFMA numerics probes: FP32 accumulation order and exactness, and FP8 FNUZ/OCP
     conversion tables checked exhaustively over all 256 codes;
   - HBM bandwidth probe against rocm-bandwidth-test on the same VM;
   - dispatch latency;
   - XCD placement effects.
5. **Model-level gates.** The existing FP64/libllama oracles for Qwen3.8-27B apply. With
   FP8 safetensors weights, new fixtures come from transformers on CPU ([big-model
   TODOs](2026-09-26-big-model-serving-todos.md)).

## 6. Open questions

- **VM access.** Is `/dev/kfd` usable in DigitalOcean/AMD Developer Cloud VMs (group
  permissions)? ROCm images imply yes. Are they SR-IOV virtual functions or full
  passthrough? That affects context save/restore, xGMI and partition modes.
- **gfx950 support.** Does the pinned LLVM assemble all the CDNA4 instructions we need?
  AMDGPUUsage lists `gfx950`. What exact `e_flags`/target string do MI355X VMs report?
- **Queue sizing per XCC.** Context-save area and scratch sizing per XCC on MI300X: how
  much memory, and what failure modes when too small?
- **Peer memory.** Mapping peer memory for multi-GPU (`MAP_MEMORY_TO_GPU` with several
  `gpu_id`s), `SDMA_XGMI` queues, and our own collectives. Latency and bandwidth probes
  are needed before designing expert-parallel all-to-all.
- **Coexistence.** Can KFD work run beside the Vulkan server on this card during
  development without disturbing benchmarks? Answering needs an explicit experiment,
  since the GPU is shared with other sessions.
