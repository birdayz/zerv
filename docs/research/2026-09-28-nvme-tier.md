# NVMe tier for prefix checkpoints — research (2026-09-28)

Latest direction: [true NVMe→VRAM PCIe P2P investigation](2026-09-28-nvme-p2p.md).
The imported-host proposal below still takes two DMA transfers. It is the fallback,
not direct storage→VRAM. P2P implementation is blocked on kernel/interface approval
and correctness experiments; no integrated disk cache exists.

Question: can prefix checkpoints (KV pages and the recurrent-state snapshot) live on
NVMe below the host tier (docs/specs/concurrent.md, "18d.5"), so the cache holds far more
conversations than VRAM + RAM, and what does the machine allow?

## Observed facts (this machine, 2026-09-28)

- Disks (`lsblk`):
  - `nvme0n1`: Samsung 990 PRO 2 TB, btrfs (`compress=zstd:3`), holds `/` and `/home`;
    87% full, 242–246 GB free.
  - `nvme1n1`: WD SN850X 1 TB (`WDS100T1X0E`), an XFS filesystem, **not mounted**.
    Contents unknown; not touched.
  - `/tmp` is tmpfs (RAM), unusable as a disk tier.
- Host RAM: 62 GB, swap 3 GB (full). The user hit a host memory limit during earlier runs.
- Checkpoint sizes (Qwen3.8-27B, f16 KV, 128-token pages):
  - one recurrent-state snapshot `snapshot_bytes` = 156,893,184 B (150 MiB; + hidden×4
    with MTP);
  - one KV page ≈ 8 MiB (16 attention layers × K+V; `Model.pageBytes`) = 64 KiB per token.
  - An 8.8k-token conversation ≈ 69 pages + 1 snapshot ≈ 700 MiB.
- Snapshot slots are capped at `max_snapshots` = 64. `checkpoint.Store` ties entry i to
  snapshot slot i, so the number of checkpoints, whatever tier their pages are on, is at
  most 64. That fits about 20–30 conversations (radix takes 2–3 checkpoints each).
- Probe `bench/disk_probe.zig` (`zerv-disk-probe FILE 4096 8 DEPTH`, 4 GiB, 8 MiB requests,
  io_uring, O_DIRECT, NOCOW directory `third_party/nvme-probe` via `chattr +C`, which also
  disables btrfs compression and checksums for those files). Rep 3 of 3:

  | buffer | depth | write | read | bytes intact |
  |---|---|---|---|---|
  | Vulkan-allocated host memory (type 6, cached) | 1 | 3.39 GB/s | 3.63 GB/s | yes |
  | Vulkan-allocated host memory | 8 | 3.37 GB/s | 5.23 GB/s | yes |
  | anonymous mmap (THP advised) | 1 | 6.31 GB/s | 6.91 GB/s | yes |
  | anonymous mmap | 8 | 6.86 GB/s | 7.20 GB/s | yes |

  - O_DIRECT works on the driver's mapping but runs at about half speed.
  - The same anonymous memory imported into Vulkan (`VK_EXT_external_memory_host`, RADV
    import alignment 4 KiB; `gpu.Buffer.initImported`, added for this probe) copies to
    and from the GPU exactly as fast as Vulkan-allocated host memory:
    - host→device 8.7–9.4 GB/s against 9.0–9.1 GB/s;
    - device→host 14.7–15.2 GB/s against 13.7–15.1 GB/s.
  - So the host store should be imported anonymous memory: disk I/O at full speed and no
    extra copy.
- `dd` sanity checks:
  - O_DIRECT 8 MiB: write 3.7 GB/s, read 6.6 GB/s;
  - buffered read 2.9 GB/s (page cache path; also pollutes RAM, which is short);
  - 32 GiB sustained O_DIRECT write 3.8 GB/s (fed through a pipe, which may be the limit),
    read back 6.7 GB/s.
- Host→device upload at ~9 GB/s is well below PCIe 4.0 x16. Noted as a separate
  question (it also bounds the host tier); not investigated here.

## Estimates (from the numbers above)

- Restoring from disk costs about 64 KiB / 6.5 GB/s ≈ 10 µs per token, plus 23 ms for the
  snapshot. Cold prefill costs about 0.75–0.8 ms per token at 4k–16k
  (docs/bench/2026-09-28-wmma-attention.md: 4,034 tokens in 2.99 s, 16,034 in 12.6 s).
  - Disk wins for any prefix longer than about 40 tokens.
  - For an 8.8k-token conversation: about 0.11 s of reading against about 7 s of prefill.
  - At 88k tokens: about 0.9 s against 100 s.
- Capacity: 200 GB holds about 280 conversations of 8.8k tokens, against about 23 in a
  16 GiB host tier.
- Write cost: a demotion to disk writes the same bytes at 3.4–6.9 GB/s, in the background
  (see below).

## Design consequences (inputs to the spec)

1. **Checkpoint count must decouple from snapshot slots.** A disk-resident checkpoint
   keeps its snapshot on disk and holds no slot. Entry → `snap: ?u32` (a slot in RAM or
   VRAM) or a disk extent. Snapshot slots become a cache of their own (the hottest
   checkpoints' snapshots), evicted to disk like pages.
2. **Asynchronous I/O is mandatory.** A synchronous 0.1–1 s read on the scheduler thread
   would stall every other stream's decode. Reads and writes go through io_uring from a
   disk worker. A restore that needs disk data becomes a pending load: the generation
   waits, and the others keep decoding. Demotion writes complete before the host pages
   (or snapshot slot) are reused.
3. **The disk tier sits below the host tier.** Pages go pool → host store → disk:
   - disk reads land in host-store pages and then take the existing promote path to the
     pool;
   - demotion to disk writes host-store pages;
   - the host store and the snapshot store become imported anonymous memory
     (`initImported`), so O_DIRECT runs at full speed.
4. **File layout.** One preallocated file (`fallocate`), NOCOW on btrfs, O_DIRECT, fixed
   extents: page-sized slots and snapshot-sized slots. Allocation is pure bookkeeping, like
   `pages.Pool`'s host store. No filesystem metadata work per demotion.
5. **Persistence across restarts is not in scope.** The file is scratch, invalid after
   exit. Persisting would need the model/tokenizer/precision fingerprint and crash
   consistency: a separate feature.
6. **Exactness:** bytes are copied unchanged. The gates are:
   - the existing batch-check round trip, extended through disk;
   - `tests/pages.zig`/`kv_system.zig` with a simulated disk that takes latency (pending
     loads).

## Open questions (need decisions)

- **Which disk.**
  - The 990 PRO (`/home`, 87% full) works with a NOCOW directory, but fills the user's
    main disk.
  - The unmounted SN850X would be a dedicated device, but mounting it is a system change
    and its contents are unknown.
- Default budget and default on or off. Proposed: off unless `--prefix-cache-disk PATH` is
  given.
- Whether internal radix nodes' snapshots are worth keeping on disk. Each costs 150 MiB;
  probably yes, since disk is cheap and a hit saves seconds.

## Source review and qualification (continuation)

Primary sources read: https://github.com/KhronosGroup/Vulkan-Docs/tree/v1.4.357
`chapters/memory.adoc` and `appendices/VK_EXT_external_memory_host.adoc`, retrieved
2026-09-28 into `third_party/vulkan-host-import/v1.4.357/`:
- memory.adoc SHA256 d53c53c4db9ae729a5abb09420cbfd3028d232527a663a597c3346c57b32c481
- extension.adoc SHA256 8eeb838a3363f8f18ab1fbf00121310ea0ba46b8c391af453e61567533601ecb

The initial imported-buffer experiment preceded the functional specification. Review found
hard-coded 4-KiB alignment, missing external-buffer capability checks and aggregate-budget
validation. These must be corrected before this API is considered verified; a driver's
pointer-properties query is not an alignment validator. The mapped range remains caller
owned; only coherent/visible memory is allowed. Source-backed ABI validation uses the
existing pinned Vulkan-Headers C probe, not handwritten structure layouts.

The initial throughput table retained only the last trial in chat, not complete raw logs;
it is exploratory evidence, not a reproducible performance gate. Anonymous memory is a
candidate, not yet a production selection. The upload probe initially lacked transfer→host
visibility and did not check the returned GPU bytes: its "bytes intact" checked disk only.
The roughly 40-token break-even estimate omits allocation, queueing, PCIe transfer and
cache lookup overhead; it is not a guaranteed threshold. None of these probes implements
an NVMe cache, asynchronous scheduling, or persisted model state.
