# NVMe → Vulkan VRAM without a host payload buffer

Research, 2026-09-28. User request: “find the most straight, DMA-ish way from nvme
to gpu vram”. This is a dependency investigation within 18d.6a, not another active
implementation track. **No P2P transfer has been executed. No NVMe cache exists yet.**
The earlier hang investigation remains closed.

## Conclusion / recommendation

The shortest payload path is **NVMe-controller PCIe peer-to-peer DMA into the GPU's
VRAM BAR**, with the CPU submitting commands/completions but never copying payload:

```
control: Zig → kernel storage interface → NVMe commands
payload: SSD controller → PCIe/root complex → GPU BAR → VRAM
```

Crossing the CPU's PCIe root complex is not a bounce through host DRAM. GPU-issued
NVMe queues are unnecessary to achieve this payload path. They add queue/doorbell,
GPU cache-coherence and device-lifecycle complexity to an already CPU-scheduled cache.

**Preferred investigation for a file-backed tier:** AMD's AIS kernel file-I/O
interface, called directly from Zig, not the C++ hipFile/HIP/HSA stack. It retains
the filesystem and kernel NVMe driver while providing the missing VRAM-to-file-I/O
bridge. Source supports a candidate chain: export Vulkan VRAM as DMA-BUF, import
into KFD, then submit `AMDKFD_IOC_AIS_OP` with file fd, KFD handle, offsets and size.
This chain is **not yet demonstrated or implementation-ready**. KFD/DRM VM setup,
Vulkan synchronization, target driver compatibility and resource lifetime need
experiments and a functional specification first.

**Shortest raw-device alternative:** a DMA-BUF-aware kernel importer pins VRAM,
maps it for the NVMe device, and supplies NVMe PRP/SGL DMA addresses to a native
queue implementation. uGDS demonstrates this mechanism in external research code;
it bypasses the filesystem and kernel NVMe driver. It is more invasive, not the
preferred default for the user's cache. Its C++ implementation is not a dependency
or code source for our engine.

Neither route works merely by enabling `O_DIRECT` in the current server. Both
require an approved kernel/system-boundary change here. Without one, the available
fallback remains **SSD DMA → imported anonymous RAM → GPU DMA → VRAM**, two payload
transfers, no CPU payload memcpy. Host import must not be called direct-to-VRAM.

## Follow-up: the most Linux-native architecture

Design judgment, not an implemented interface: retain filesystem ownership and the
kernel NVMe driver; integrate GPU memory with the normal direct-I/O/block path.
Use DMA-BUF for cross-driver allocation sharing, PCI P2PDMA/DMA mapping for device
addresses, and explicit synchronization/lifetime management. The filesystem owns
file extents and the kernel owns queues, resets, permissions and device removal.
A normal cache file can then coexist with other files; exclusive controller
ownership is a property of the raw-queue alternative, not of P2P itself.

The missing generic file-I/O handoff for GPU memory remains substantive kernel
integration work, not an existing `io_uring` DMA-BUF option or a tiny wrapper.
AIS is one vendor-specific implementation of this kind of bridge, but is absent
on the installed driver. For true P2P, prefer upstream-compatible subsystem
integration over kprobes/private queue layouts or raw extent access. No upstream
acceptance or completed design is claimed. For unchanged-system implementation
now, ordinary file direct I/O through imported host staging is the Linux-native
fallback, explicitly two DMA transfers rather than direct-to-VRAM.

## Why mmap + pread / io_uring is not the bridge

Linux's P2P documentation distinguishes MMIO without `struct page` (typically
wrapped in DMA-BUF) from `MEMORY_DEVICE_PCI_P2PDMA` pages. The former cannot be
passed as an ordinary pointer to `read/write`, even with `O_DIRECT`. The latter
can work in audited direct-I/O paths supporting `FOLL_PCI_P2PDMA`.

TTM's VRAM mmap path sets `VM_PFNMAP | VM_IO`. An ordinary CPU-visible Vulkan VRAM
mapping is not proof of pinnable userspace pages. io_uring's ordinary registered
buffers use `FOLL_LONGTERM`; Linux explicitly forbids long-term pinning of P2P
pages. Registering such a pointer does not turn it into a storage DMA target.

The inspected io_uring registration and NVMe ioctl UAPIs provide no general
“file fd + VRAM DMA-BUF fd” operation. The kernel NVMe driver supports P2P
payloads, but the userspace-to-kernel memory handoff is missing on this stack.
Do not confuse io_uring command passthrough with an arbitrary physical-address ABI.

## Route A: native calls to AMD's AIS kernel interface

Primary code reviewed in ROCm/amdgpu at `48f2f4486a8dc6122195fa8755b6a1a6ee2ad3e2`:

- `kfd_ais_init`: for a large-BAR discrete GPU, registers a P2P resource for BAR0
  using `pci_p2pdma_add_resource`. This creates the device-page representation
  missing from ordinary VRAM mappings and consumes host memory for page metadata.
- `kfd_ioctl_import_dmabuf`: returns a KFD object handle for a DMA-BUF import.
  Upstream `import_obj_create` preserves a VRAM-preferred object's VRAM domain.
- `kfd_ioctl_ais`: looks up the KFD object, requires VRAM, retains and pins the BO
  in VRAM for the operation, then unpins after completion.
- `kfd_ais_rw_file`: resolves the file's storage device, checks P2P distance,
  obtains VRAM SG information, builds P2P `bio_vec`s, and invokes
  `vfs_iocb_iter_read/write` with direct-I/O semantics when `O_DIRECT` is set.
  The normal filesystem/block/NVMe path submits the payload to VRAM. The ioctl
  returns transferred bytes and status; it is synchronous, so a bounded worker
  would be needed rather than blocking the serving scheduler.
- `kfd_ioctl.h`: `AMDKFD_IOC_AIS_OP` accepts handle, handle offset, file offset,
  size, op and file fd. No C++ userspace library is intrinsic to this ABI.
  Current rocm-systems `libhsakmt/src/ais.c` confirms the thin ioctl handoff;
  its runtime address-to-handle bookkeeping is not something we need to import.

Current hipFile compatibility documentation supports XFS or ext4 `data=ordered`
on local NVMe (also qualifying LVM-on-NVMe), with AIS-capable amdgpu. **The current
btrfs mount does not qualify, and the loaded driver lacks AIS.** Master kernel
source contains broader storage work, but that is not a verified support promise
for our filesystem/card. Do not install an arbitrary development driver based
only on finding these functions. Mounting the WD would solve neither driver
support nor Vulkan/KFD interop by itself.

A future proof must establish exact buffer export support, correct native KFD
process/VM initialization, same-GPU import without host migration, pin lifetimes,
external ownership/cache synchronization and actual data correctness. We have
not established a compatible AIS driver release for Arch 7.2.6 + Navi31.

## Route B: DMA-BUF importer + direct NVMe queues

uGDS at `0fcba71948b79121984087a38caabc7d3663e5d8` demonstrates:

1. Export GPU allocation as DMA-BUF (its AMD path uses HSA; Vulkan also defines
   this export mechanism).
2. Kernel `dma_buf_get` → dynamic attach to NVMe PCI device with
   `allow_peer2peer=true` → reservation lock and pin → wait existing fences →
   `dma_buf_map_attachment`.
3. Flatten the resulting SG **device DMA addresses**, not CPU pointers or guessed
   BAR offsets, into NVMe page-address lists. CPU submits and polls NVMe commands;
   the controller moves payload directly to/from VRAM.

Its README explicitly bypasses kernel NVMe/filesystems. This needs exclusive,
authorized storage ownership/rebinding, not raw writes to extents discovered in
a mounted btrfs file. It cannot safely be treated as an incidental probe of the
user's main drive or the unmounted WD.

Important caveats from reviewed source:

- amdgpu DMA-BUF mapping may **fall back to GTT (host RAM)** if an attachment
  cannot do P2P. Successful import or fast I/O alone does not prove direct VRAM.
  The probe must demonstrate actual VRAM residency and the NVMe-to-VRAM mapping;
  fail closed if that cannot be established.
- Buffer lifetime, outstanding DMA, reset/removal, IOMMU mappings and revocation
  are kernel responsibilities, not safe to replace with `/proc/pagemap` guesses.
- uGDS does not publish a DMA-reservation completion fence for its bypass I/O;
  userspace must enforce GPU/storage exclusivity. On Linux >=7.1 it omits
  `invalidate_mappings`, relying on pinning. That is a lifecycle audit item,
  not an accepted correctness argument for zerv.
- ROCm XIO is another research example, but its NVMe module uses kprobes and
  private NVMe queue-layout knowledge to intercept queue setup. Its own pinned
  performance report has device-memory **multi-LBA write verification failures
  on both tested SSDs**, plus a random-device-memory timeout on one. Not a clean,
  validated production shortcut. None of its performance claims were reproduced.

A custom filesystem-preserving DMA-BUF helper on the current upstream driver is
not automatically small: the existing VRAM SG export does not by itself provide
the P2P `struct page` representation required by the normal filesystem path.
AIS's driver integration addresses precisely that missing layer.

## Vulkan side / proposed acceptance gate

The relevant export is `VK_EXTERNAL_MEMORY_HANDLE_TYPE_DMA_BUF_BIT_EXT`, **not a
promise that any `OPAQUE_FD` is a DMA-BUF**. Query exact usage through
`vkGetPhysicalDeviceExternalBufferProperties`, create an external-capable buffer,
allocate compatible exportable device-local memory (honor dedicated-only), then
`vkGetMemoryFdKHR`. The caller owns the returned fd. Imported references and
in-flight operations must finish before allocation reclamation.

NVMe is a foreign device, not another queue of the same Vulkan driver. Resolve
`VK_QUEUE_FAMILY_FOREIGN_EXT` support and explicit release/acquire cache-visibility
requirements. An NVMe CQ completion alone is not a Vulkan GPU-cache barrier.
No concurrent GPU access while storage owns a destination/source range; completion
and ownership must be represented in scheduler state, without device-wide waits
in the eventual steady-state path.

Before implementing production support, spec and executable gates must cover:

- Exact pinned driver/API, independent C-header ABI fixtures, strict capability
  rejection, bounded allocations/queues, checked alignment and offset arithmetic.
- Read-only import/mapping capability test first; it should need no disk writes.
- Then **an explicitly approved scratch file or disposable namespace only**:
  seeded known bytes written conventionally, direct SSD→VRAM read, GPU verification
  and readback vs the CPU fixture; GPU-written bytes→SSD→ordinary CPU read compare.
  Bitwise exact, including multi-LBA, SG boundaries, offsets and guard regions.
- Prove VRAM rather than GTT residency; instrument the selected mapping/path.
  Handle shorts/EOF, sparse extents, failures, cancellation, teardown and resource
  pressure; never free memory on timeout while DMA could still be active.
- Only after those pass: repeated ABBA staged-vs-P2P component trials on identical
  sizes/depths (including ~8 MiB KV pages and ~150 MiB snapshots), CPU/memory cost,
  interference with inference; then full serving and tuned llama-server gates.

These are proposed gates, not passed tests. There is **no measured P2P throughput
or serving speedup** in this report.
