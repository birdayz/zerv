# Native zerv vs llama-server — Qwen3.8-27B Q4_0 serving, 2026-09-22

**Result: zerv serves Qwen3.8-27B natively over `POST /v1/chat/completions`
(JSON and SSE) with greedy output matching llama.cpp.** Decode is faster than tuned
llama-server at short context (+10%), about equal near 300 tokens, and slower as
context grows (−16% at 0.9K, −44% at 3.2K). **Prompt processing is 3–32× slower**,
because prefill runs the one-token decode step once per prompt token. zerv is **not**
the faster server overall on this workload.

## Setup

RX 7900 XTX (RADV 26.2.3), Ryzen 9 3900X, same SHA-pinned `Qwen3.8-27B-Q4_0.gguf`,
same official chat template, context 8192, one slot, greedy (temperature 0, seed
1234), streaming with usage. Client: Python `http.client` over SSE, one request at
a time; TTFT = first reasoning/content delta; decode rate = (completion tokens − 1)
/ (last delta − first delta). One warmup request per case, then 3 repeats per case,
engines strictly one after another. Whole benchmark run twice. Workload:
[serving-v2.json](../../bench/workloads/serving-v2.json) (23/81/836/3223-token prompts).

llama-server build 10964 (b29c606e), all layers on Vulkan0, `--jinja` with the
official template file, `--reasoning-format deepseek`, `--cache-ram 0`, no
speculation/context shift. Configurations: flash attention on/off, ubatch 256/512,
and a partial precision control (`GGML_VK_DISABLE_MMVQ=1`, F32 KV).

**Correction (same day):** that control is precision-matched for decode only. The
pinned ggml source (`ggml_vk_mul_mat_q_f16`) shows that prompt processing on this card
still quantizes activations to Q8_1 for integer-dot matmul (MMQ), with FP16
cooperative-matrix paths also available. So llama-server's prefill numbers in this
report are for lower activation precision than zerv's FP32 prefill. A fully FP32
llama control additionally needs `GGML_VK_DISABLE_INTEGER_DOT_PRODUCT`,
`GGML_VK_DISABLE_COOPMAT` and `GGML_VK_DISABLE_F16`; it is measured in the prefill report. Exact commands,
binary/model/template/workload hashes: [run1 manifest](data/2026-09-22-serving-v2-run1/manifest.json),
[repeat manifest](data/2026-09-22-serving-v2-repeat/manifest.json). The zerv binary
rebuilt from source is byte-identical to the one benchmarked
(`0256adbe…da175a`).

## Output equality

Every engine was deterministic: one distinct output per case across all repeats and
both runs. zerv's text equals every llama-server configuration on 3 of 4 cases. On
`decode-think` the tokens are the same, but llama-server keeps a trailing `\n` at the
end of `reasoning_content` and zerv trims it. That is a response-formatting difference,
not a model difference. zerv's trimming rules were chosen by us and are not yet checked
against llama.cpp's reasoning parser.

**Correction (2026-09-22, block 12b).** Re-reading the raw data shows the statement
above holds only for `llama-f32` and `llama-fa-ub256`. On `decode-think`,
`llama-fa-ub512` and `llama-nofa-ub512` produce a different greedy continuation
from about character 300 (366 vs 355 characters). That is a numerical divergence,
not formatting. The trailing-newline difference is now fixed, and zerv equals the
FP32/ub256 configurations byte for byte. See the
[12b report](2026-09-22-serving-open-items.md).

Independent end-to-end gate (`tools/check_session.py`,
[report](data/2026-09-22-session-gate/report-run1.json)): for both oracle cases the
server's greedy output, token counts and finish reason equal the libllama greedy
continuation, in JSON and SSE modes. Numerical model gates: [forward-pass report](2026-09-22-model-forward.md).

## Interpretation

- **Prefill is the dominant loss.** zerv prefill costs one decode step per token
  (~23–34 ms each); llama-server batches the prompt (~930 tok/s at 3.2K). Batched
  prefill (matrix-matrix projections, chunked DeltaNet) is the first optimization target.
- **Decode matches or beats llama-server at short context**, then falls off with length.
  zerv's attention kernel uses one workgroup per query head (24 workgroups) and scans the
  whole KV cache serially per thread. At 3.2K context the step time roughly doubles.
  A split-K (flash-decoding) attention kernel is the second target.
- This is single-request latency only. No concurrency, batching or prefix caching on
  either side, and only the installed llama-server build was measured; other
  competitors (newer llama.cpp, HIP builds, vLLM) remain untested.

## Failed and invalidated runs (retained)

- [serving-invalid-buffered](data/2026-09-22-serving-invalid-buffered/INVALID.txt):
  SSE deltas were held in the HTTP body writer's buffer, so zerv's TTFT/decode
  timings were wrong (e.g. an impossible 210,607 tok/s). Fixed. A regression test
  proves each delta reaches the socket before generation continues; the test fails
  without the fix.
- [serving-failed-run2](data/2026-09-22-serving-failed-run2/FAILED.txt): workload
  v1 sent `reasoning_effort: "high"`. zerv maps it to the template's `xhigh`, while
  llama-server passes it to the template, which raises (HTTP 500). Workload v2 uses
  `xhigh`. This is a real API difference between the two servers.

**Correction (2026-09-23).** This report calls llama-server's default prompt path "Q8_1" (integer-dot activations). On this card that is wrong. With `KHR_coopmat` available, ggml converts activations to f16 and uses `matmul_quant_f16_f16acc`: f16 weights and activations with f16 accumulation on WMMA. Q8_1 is used only when cooperative matrices are disabled. The timings above are unaffected. Evidence: [llama precision](2026-09-23-llama-precision.md).
