# 2026-09-22 — matched libllama tokenization and two native optimizations

## What is actually compared

**Direct native vs direct libllama, not native vs HTTP.** Both execute in-process
with the same NFC input bytes and exact expected IDs/raw bytes. The reference is
the very same installed library used by the actual llama-server, not a surrogate
Python implementation. The old [HTTP table](2026-09-22-tokenizer.md) is retained
with a correction; it is not tokenizer-speed evidence.

[Contract](../specs/tokenizer-matched-benchmark.md),
[reference usage/build audit](../research/tokenizer-comparison-fairness.md).
The pinned handler → tokenize_mixed → common_tokenize → llama_tokenize call chain
was inspected. Our C wrapper uses the same one-call byte-count output-capacity
policy and special flags. It does not query capacity by tokenizing twice, request
offsets, initialize vocabulary inside timing, or serialize requests in the loop.

Encode includes per-call owned output allocation/free on both sides. Native uses
smp_allocator; reference uses libc/C++ allocators. Decode writes whole-sequence raw
bytes into preallocated storage, no lossy per-piece UTF-8 decode. An additional
`llama-preallocated` encode control removes the reference's outer output allocation
from timing; it favors llama and is labeled separately rather than misrepresented
as matched ownership. The initial allocation audit changed reference medians by
only 0.8–1.6%; the wrapper is not responsible for the observed large gap.

## Setup and correctness

Ryzen 9 3900X, Linux 7.2.6, Zig 0.16.0 ReleaseFast/native. Installed Arch llama-cpp
0.4.1-1, build10964/b29c606e28, GCC 16.2.1; exact header/lib/model/adapter/compiler
hashes and dynamic loader resolution in each manifest. Native ELF has no dynamic
NEEDED dependency; C/libllama stays in test tooling. Package BUILDINFO records LTO,
but full reference compilation flags and a best native-tuned build are **not**
established. This is a result against the installed build, not all llama builds.

- Original 1,240 plus **17,793 newly generated independent HF cases = 19,033 exact
  encode cases**, 70 raw decode cases, all 248,320 token pieces on the actual GGUF.
  New cases include all ASCII pairs and seeded short/heap boundaries. Fixtures
  were generated before optimized code and regenerated byte-identically.
- Both native paths preserve forward ranks, leftmost ties, decode-only tokens,
  added-token matching, normalization and resource limits. Synthetic rank/tie and
  both short/long allocation-failure paths are explicitly tested.
- **26/26 native tests pass Debug and ReleaseFast; 28/28 Python tests pass.** Full
  actual-GGUF checks and exact reference outputs gate every measured variant.
- Changed-NFC cases are normalized independently for correctness comparisons;
  every timed workload already is NFC. Native still runs normalization and UTF-8
  validation. No claim that llama offers equivalent normalization on arbitrary text.
- C adapter rejects empty/bad-header/truncated/trailing/count-overflow corpora;
  [negative outputs](data/2026-09-22-tokenizer-byte-pairs-repeat/adapter-negative-tests.json).

Three warmups; seven trials per operation/workload, three alternating engine-order
rounds: **21 observations**. 100 encode or 1,000 raw-decode calls per timed trial.
No HTTP/Python/JSON/hashes/validation in either timed loop. Warm vocab, repeated
fixed inputs, no native cross-request result cache. Model load/vocab init excluded.

Initial runs used CPU 2. Other host work and powersave frequency policy caused
substantial drift; neither was changed/stopped. A paired repeat and subsequent
runs pin **all engines to CPU 10** (quieter in an observed sample, not exclusively
reserved). Saved pre-optimization and optimized binaries are interleaved in the
same run and checked against the exact same corpus. Baseline SHA/source snapshots
are verified before reuse. Do not subtract different-core historical timings.

## Optimizations, implemented sequentially

1. Instrumentation in an ignored research copy found many tiny pieces paying
   linked-symbol/heap overhead. <=16-byte pieces now use stack IDs and cached
   adjacent rules, scanning by rank with leftmost ties and rescanning newly formed
   lower ranks. Longer pieces retain the heap. One byte appends directly.
2. All 65,536 initial byte-pair rules are indexed directly, avoiding general
   hash-map probes on initial edges. Built only from validated merges; arbitrary
   byte-root IDs remain supported. Newly formed edges use the general map.
   **Tradeoff: +524,288 owned bytes and one vocabulary-init allocation.** No prompt
   result cache, no per-request table build, no narrowed tokenizer behavior.

Instrumented [stage counts/timings](data/2026-09-22-tokenizer-profile-baseline/1.stderr)
and [method](data/2026-09-22-tokenizer-profile-baseline/manifest.json) are reproducible
with `bench/profile_tokenizer.py`. Per-piece clock probes perturb timing; these are
cost-location evidence, not absolute uninstrumented stage times. Multilingual NFC
and long-piece heap work remain substantial.

## Repeatability, marginal gains and losses

The preceding full final-code run (`byte-pairs`) had optimized encode medians:
ascii 52.087 µs, multilingual 94.019 µs, chat 6.545 µs, long_word 813.453 µs, unicode_long 275.763 µs, unique_code 148.364 µs.
It showed a **2.0% long-word regression**, while this repeat shows a 5.3% reduction.
The long-word sign changes and dispersion do not establish a stable gain. Keep
both observations, not just the favorable repeat. Unicode-long improvement is
modest/variable as well; this is primarily a short/mixed-piece optimization.

A separate same-run incremental comparison against the **short-scan-only** binary
isolated the direct byte-pair table's contribution:

| Workload | Short scan only µs | Plus byte-pair table µs | Change |
|---|---:|---:|---:|
| ascii | 56.771 | 52.069 | -8.3% |
| multilingual | 101.358 | 94.438 | -6.8% |
| chat | 7.118 | 6.500 | -8.7% |
| long_word | 801.602 | 810.734 | +1.1% |
| unicode_long | 281.900 | 273.398 | -3.0% |
| unique_code | 174.752 | 147.748 | -15.5% |

The table is retained for its repeatable short/mixed benefits, with the explicit
512 KiB memory cost and the small observed long-word loss. No universal throughput,
serving, cold-cache, concurrency, or fastest-implementation claim follows.
