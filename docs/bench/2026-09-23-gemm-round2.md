# Prefill GEMM, round 2: what limits the wide kernel (block 13i, research; closed without a change)

Date: 2026-09-23. Question: after 13h, the wide (256×64) Q4_0 kernel runs at 33–36
TFLOP/s against a clock-adjusted FP32 FMA peak of about 55. Where does the rest go?

## Ablations

Source: [ablation-wide.comp](bench/data/2026-09-23-gemm-round2/experiments/ablation-wide.comp),
generated from the shipped `gemm.comp`. The base build is byte-identical to
`gemm_q4_0_w.spv`. Substitutes are derived from a runtime word, so nothing is
constant-folded. 600 samples at 512 rows, natural split. Raw data:
[ablation-r1.jsonl](bench/data/2026-09-23-gemm-round2/ablation-r1.jsonl).

| Variant | ffn_gate TFLOP/s | attn_qkv TFLOP/s |
| --- | --- | --- |
| shipped wide | 35.8 | 33.4 |
| no dequant | 37.1 | 35.2 |
| no LDS reads | **45.6** | **41.8** |
| no barriers | 35.6 | 33.3 |
| no X loads | 20.6 (**invalid**, see below) | 20.1 |

- **Invalid variant.** The X substitute moved X from scalar to vector registers (VGPRs
  192 → 204, 8 → 6 waves per SIMD). It measures that change, not the cost of X loads.
  The same applies to the combined "compute only" variants (27–29 TFLOP/s).
- **LDS reads are the largest single cost (+27%).** The substitute's own VALU work is
  included, so the true share is at least that.

## ISA of the shipped wide kernel

The loop body is shown in [wide-q4_0-isa.txt](bench/data/2026-09-23-gemm-round2/wide-q4_0-isa.txt)
(BB8/BB10):

- The source issues the next pair's X loads (`s_buffer_load_b64` × 16) before the
  current FMAs.
- The compiler instead sinks those loads into the loop latch (BB10), after the FMAs.
- The loop head then issues the LDS reads and waits `lgkmcnt(0)`, which also covers
  the just-issued SMEM loads.
- SMEM and LDS share `lgkmcnt`, and SMEM returns out of order. So the full SMEM
  latency is exposed once per 2 k (128 FMAs per lane); only the other waves on the
  SIMD hide it.

## Tried

| Variant | Result |
| --- | --- |
| LDS A reads pipelined one pair ahead as well ([gemm-apipe.comp](bench/data/2026-09-23-gemm-round2/experiments/gemm-apipe.comp); bit-identical; VGPRs 192, 8 waves) | 1–3% slower on every shape ([steps-r1.jsonl](bench/data/2026-09-23-gemm-round2/steps-r1.jsonl)) |

From 13h (the narrow kernel), none of these helped either:

- 2 kb per iteration;
- kb-pair ping-pong;
- a forced load order;
- X through VMEM;
- a no-LDS direct kernel.

## Conclusion

The remaining gap is LDS read cost plus exposed SMEM latency. The compiler's
scheduling undoes source-level software pipelining. Options not tried, each with a
cost:

- Immediate SMEM offsets. These need a compile-time X row stride, meaning
  per-K-specialized modules or a fixed-stride activation layout.
- Hand-scheduled SPIR-V or ISA. This is outside the current toolchain policy.

No change was made. The block is closed as research with a negative result. The
kernel remains at the 13h state.
