# Paged KV addressing, single sequence (block 18b.1) — 2026-09-24

**Question.** Does the paged KV layout ([spec](../specs/concurrent.md), "Addressing": 256-token
pages, a page table in the activation arena) leave every output bit unchanged with one
sequence and the identity table? What does the indirection cost?

**Answer.** Every gate is byte-identical to the pre-change build. (The page size became the
knob `--kv-page-tokens`, default 128, below.) Speed: decode −0.24% at
position ~615, +0.14% (f32 KV) / +0.33% (f16 KV) at ~30k; prefill −0.1 to −0.15%. The long-context
decode cost is all in `pv` (+2 to +4%); hoisting the page-table load did not change it.

## Change

- `src/model/layout.zig`: `kv_page` (256), `page_piece`, `pagesFor`, `State.pages`,
  `State.pstride`/`layersIn`. `kcache`/`vcache` are now in-page piece offsets. `maxContext`
  counts whole pages. New region `Act.ptab` (u32 per page) at the end of the arena, before
  `x16`.
- Shaders (`model.comp` qkprep, scores, pv, qk_b; `flash.comp`): trailing push words `ptab,
  pstride`. Token `j` is at page `actu[ptab + j/256]`, in-page `j%256`. K is
  `[kvh][d][256]` and V is `[kvh][256][d]` per page and layer. Only the 10 KV-touching modules
  changed (5 kernels × f32/f16 KV). Rebuilt with `tools/compile_model.py`. The installed set
  equals a fresh compile (manifest sha256 `0fedfe22…`).
- `runtime.zig`: the 12 KV push sites set `.ptab/.pstride`. `writePageTable` copies the identity
  table in once at init; `reset` does not touch it. KV buffers are sized by pages.
- Tests: `tests/model.zig` layout and push-size expectations are paged. The three
  GPU kernel tests in `tests/model_gpu.zig` (split-K decode attention, fused prefill attention,
  f16 KV writers) now use a helper `Paged`. It is independent of the kernels and uses a
  **permuted** table over more physical pages than needed, with the layer second in its
  buffer. Every unmapped page and the other layer's pieces hold NaN or huge sentinels. The
  writer test crosses a page boundary (positions 255, 256) and checks that no other element
  was written.
- Tools: `tools/verify_model.py --tool PATH` reruns a gate with an archived capture binary.
  `bench/race_profile.py` is a new interleaved (ABBA) A/B harness for `zerv-model-profile` binaries.

- Prefill K writes are faster: consecutive positions of one dimension are within 256 elements
  instead of `ctx` apart.
- `pv` at long context is slower. **Tried:** loading the page entry at kernel entry, so its
  latency overlaps the softmax (and in `scores`, the Q staging). Race `long-f32kv-hoist`:
  `pv` 2.738 against 2.738 unhoisted, no change. It was reverted; the installed shaders are the
  gated ones. **Not measured:** the working hypothesis is address-translation/DRAM locality. A head's V
  was one contiguous run and is now 1 MiB pieces 32 MiB apart (f32, 16 layers per buffer).
  That is roughly twice the 2 MiB regions per pass.
- Serving TTFT/decode in the identity run matched the earlier native-gemm run within noise
  (not interleaved, so no claim).

## Page size knob (`--kv-page-tokens`), default changed to 128

**Change.**
- `KV_PAGE` is now specialization constant 0 of the 10 KV modules.
- `gpu.Kernel.Options.constants` passes it ([gpu-driver spec](../specs/gpu-driver.md)).
- `Model.Options.kv_page_tokens` and `--kv-page-tokens N|context` select the page size.
  `context` means one page of the whole context: the pre-paging layout, plus a one-entry page
  table.
- The resolved size is `layout.State.page`.
- The `Act.ptab` region is sized for the smallest page (128), so the activation arena does not
  depend on the knob.
- Tools: `model_capture` `CONTEXT@page=N`, `zerv-model-profile … KV@page=N`,
  `verify_model.py --kv-page-tokens`, and per-engine arguments in `race_profile.py`
  (`NAME=PATH|ARGS`). The server logs `zerv: KV cache: N pages of P tokens` and the capture
  tool logs `kv_pages=NxP`.

**The constant costs nothing.** `RADV_DEBUG=shaders` dumps of the 18b.1 profiler (`#define
KV_PAGE 256u`) and of the specialization-constant build (P = 256) give identical machine code
for all 74 pipelines (49,088 instruction lines, compared as a multiset of per-pipeline hashes).

**A silent test gap found and fixed.** The first version of the page-size tests passed without
checking anything at 128-token pages. The test helper used `std.debug.assert(physical % 7 !=
0)`, and with 32 pages, physical = 35. In ReleaseFast a failed assert is undefined behaviour,
not a panic. LLVM dropped the rest of the function; the test returned early and reported OK,
and the second call in the same test never ran. It was caught because a check print was missing.
The helper now picks a valid physical count itself (no assert), and every attention case prints
its page size and worst error. The 18b.1 cases (256-token pages: 19, 19 and 5 physical pages)
were not affected. Rule recorded in [verification.md](../specs/verification.md).

**Speed** (`race_profile.py`, ABBA, one binary per page size plus the pre-18b.1 binary `pre`;

| 30k, f16 KV, prefill total | 29916 | 29924 | 29886 | 29881 | — | 29922 |

- The page table load is free: `context` equals `pre`. What costs is the split into pieces.
- 128-token pages are the closest to `pre` at 30k: +0.06% (f32 KV) and +0.07% (f16 KV), against
  +0.18% / +0.39% for 256. With f16 KV the 128 and 256 ranges do not overlap. At 4k, 128 and 256
  tie, and both are 0.3% under `pre`. Prefill does not change beyond noise (±0.2%). Prefill
  `qkprep` is fastest at 128 and 256 (47 / 53 ms against 68–76 ms for the larger pages).
- By phase the picture is mixed: at 128, `scores` is the fastest of all layouts and `pv` the
  slowest (f32 KV). The mechanism is not measured.
- **Decision:** the default is now **128**. It is equal or better everywhere measured, and it
  halves the pool's rounding waste per sequence (half a page on average: 8 instead of 16 MiB
  with f32 KV). 128 is also the smallest valid page. `--kv-page-tokens context` keeps the
  pre-paging layout selectable.
