# vLLM as a competitor on the RX 7900 XTX — 2026-09-25

**Question.** vLLM is the reference multi-user serving engine: paged attention, continuous
batching, chunked prefill and prefix caching. How does it compare with zerv and llama-server
on this card and model, for one user and for several?

**Answer so far (multi-user, 8 slots; [full tables](2026-09-25-multiuser.md)):**
- **vLLM wins two metrics:**
  - 8-user aggregate throughput: 158.2 tok/s against zerv's 150.9 (+4.8%);
  - steady token gap p99: 51–53 ms against 147.
- **zerv wins the rest:**
  - 1 user: 48 against 36 tok/s (vLLM's best round);
  - 2 and 4 users: 87 / 139 against 51–63 / 99–108 tok/s;
  - 8-user TTFT p50: 0.44 against 0.78–1.07 s;
  - worst steady gap: 191 against 430–791 ms;
  - a long prompt arriving mid-stream: running users keep 40 tok/s against 5.7–13, and a short
    prompt behind it waits 1.4 s against 4.8–5.4 s.
- **Single user with speculation** (vLLM MTP against zerv MTP): not yet run.

## Setup

**Image.** `vllm/vllm-openai-rocm:v0.30.0`, pinned as
`sha256:2e7da1ad1c66836802072588adea75f9f4991da5f9545b4318e91d422c22ce6a`.
- Published 2026-09-22 by vLLM's official Docker Hub org. AMD's `rocm/vllm` repository
  describes itself as release-candidate images and points to this one.
- Built with `PYTORCH_ROCM_ARCH=gfx90a;gfx942;gfx950;gfx1100;…`, so it includes our gfx1100.
- Entrypoint `vllm serve`; 49 GB unpacked.

**Weights.** `RedHatAI/Qwen3.8-27B-INT4`, revision `c063053e004e9783631651df95cf55d0bbf88b32`
(RedHatAI is the quantization org of the vLLM maintainers).
- Scheme (from `recipe.yaml` and `config.json`): W4A16, symmetric INT4 with group size 128,
  GPTQ with AWQ smoothing, calibrated on 512 samples. Embeddings, lm_head, the vision tower and
  DeltaNet `in_proj_a`/`in_proj_b` stay BF16. The checkpoint declares an FP8 KV cache.
  Includes an MTP head (`model_mtp.safetensors`).
- **Not the same weights as zerv/llama-server** (Q4_0, round to nearest, group 32, from
  `unsloth/Qwen3.8-27B-GGUF`). Speed is compared here; quality needs its own comparison.
- The checkpoint's `chat_template.jinja` is byte-identical to the official template that
  llama-server gets via `--chat-template-file` (sha256 `c3cf9e34…`). vLLM gets the same file,
  so prompts render identically.
- 12 files in `models/RedHatAI/Qwen3.8-27B-INT4/c063053e…/`; `MANIFEST.json` there lists
  every file's sha256.

**Safety checks before first use** (user requirement: check downloads for malware):
- **Provenance:**
  - the image comes from vLLM's official org, pinned by digest;
  - the weights come from RedHatAI at a full commit sha;
  - ClamAV (`clamav/clamav@sha256:0e31ce08…`, the ClamAV project's official image) has
    signatures main 63, daily 28134 and bytecode 339.
- **Weights: nothing executable.** `tools/fetch_hf.py` (new) accepts only safetensors,
  JSON, text, jinja, YAML and Markdown. It refuses pickle checkpoints, Python, shared
  objects, scripts and archives, and any `config.json` with `auto_map` (custom code). vLLM
  runs without `--trust-remote-code`.
- **Weights: integrity.** Every file matches the Hub's sha256 (LFS) or git blob sha1.
  Both safetensors files parse: a JSON header with known dtypes, and tensors that tile the
  data section exactly, with no gaps, overlaps or trailing bytes (2,016 and 15 tensors).
  `tools/fetch_hf.py --verify` re-checks.
- **ClamAV scans** (`clamscan` 1.5.4, 3,628,083 signatures, 8 parallel scans):
  - image filesystem (`docker export`, 35 GB, 154,348 files): **0 infected** among the
    149,039 files scanned. 5 files over 1 GB exceed ClamAV's limits (`_rocm_C.abi3.so`,
    `libMIOpen.so`, the rocFFT kernel cache and two static libraries); the list is in
    `third_party/vllm/scan/skipped-rootfs.txt`.
  - weights: **0 infected** in 13 files. ClamAV cannot read files over 2 GiB, so
    `model.safetensors` (18.6 GB) is covered by the hash and structure checks above.
- **Container runtime restrictions:**
  - `--user` (our uid), `--cap-drop ALL`, `--security-opt no-new-privileges`;
  - only `/dev/kfd` and `/dev/dri/renderD128`;
  - weights and template mounted read-only; the only writable mount is
    `third_party/vllm/cache`;
  - the API published on 127.0.0.1 only;
  - `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `VLLM_NO_USAGE_STATS=1`, `DO_NOT_TRACK=1`
    (`bench/run_serving.py`, `vllm_engine`).

**vLLM flags:** `--max-model-len` (per request), `--max-num-seqs` (concurrency),
`--gpu-memory-utilization 0.92`, `--limit-mm-per-prompt '{"image":0,"video":0}'` (text only),
`--reasoning-parser qwen3`, `--no-enable-prefix-caching` (cold prefill, as for the other
engines). `vllm-mtp3` adds `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`,
the model card's recommendation.

**Harness changes:**
- `run_serving.py`: engines `vllm`, `vllm-mtp3`, and `llama-fa-b512` (llama-server with
  `-b 512`: at most 512 prompt tokens per server step, fewer stalls for running users).
- `run_multiuser.py` and `run_concurrent.py`:
  - set `--max-num-seqs` and `--max-model-len` for vLLM;
  - run the engine's `stop` command (`docker rm -f`) after a run;
  - use a per-engine readiness timeout (30 min for vLLM's first compile).
- Clients read vLLM's `reasoning` delta field as well as `reasoning_content`. The GPU-busy
  check matches vLLM processes.

## Bring-up findings

- **Running as our uid** needs `USER`/`LOGNAME` set: torch calls `getpass.getuser()`, and
  the image has no passwd entry for uid 1000.
- **The KV cache is FP8.** vLLM takes the checkpoint's `kv_cache_scheme` (8-bit float,
  per-tensor static scale): the attention selector logs `kv_cache_dtype=fp8`, although the
  engine config prints `auto`. This is the checkpoint's intended deployment, and less KV
  precision than zerv's f16 and llama-server's f16.
- **A cold compile does not fit next to the model on 24 GB.** Starting a configuration the
  first time compiles the graph (~55 s). Profiling then finds −0.5 to −1.2 GiB for the KV cache
  and the server exits. The same configuration starts on the next attempt, once the compile
  cache is warm: 3.6–3.8 GiB of KV (67–72k tokens, 8.2–8.8 requests of 8,192 tokens), ready
  after ~67 s.
  - Observed 4 times across `--max-num-seqs 1` and `8` and chunks of 512 and 2048
    (`third_party/vllm/smoke/`).
  - The benchmark's first attempt failed this way ([data](data/2026-09-25-multiuser/failed-vllm-cold-compile/)).
  - Every benchmarked configuration is now warmed first. That is setup, not measurement.
- **Memory at `--gpu-memory-utilization 0.95`:** weights 16.77 GiB, CUDA graphs 0.9–1.35 GiB,
  peak activations ~1.2 GiB; 23.8–23.9 GiB of VRAM in use while serving. At 0.92 there is no
  room for the KV cache.
- **Attention backend** `ROCM_ATTN`, with a Triton fallback for paged decode ("Cannot use ROCm
  custom paged attention kernel"). The DeltaNet layers run vLLM's Triton GDN kernels.
- **Smoke test:** "17·23" answered 391 and a haiku came out sensible. Single user: TTFT
  0.16–0.18 s at ~60 prompt tokens, decode ~38–39 tok/s.

### Single user (binary `7022f1aa`, `third_party/vllm/single-user.sh`)

Each engine ran alone, 2 repeats, greedy. vLLM configs were warmed first (the MTP config failed
its first cold start, as above). [decode-v1 data](data/2026-09-25-vllm/decode-v1/),
[serving-v2 data](data/2026-09-25-vllm/serving-v2/).

Decode tok/s, decode-v1 (512 tokens; code / json / think / prose):

| Engine | code | json | think | prose |
| --- | --- | --- | --- | --- |
| **zerv, MTP 3 drafts** | **122.7** | **127.2** | **109.3** | **76.8** |
| llama-server, MTP 4 | 106.8 | 112.9 | 92.0 | 59.2 |
| vLLM, MTP 3 | 69.7 | 75.6 | 64.0 | 46.2 |
| zerv, no speculation | 51.5 | 51.6 | 51.1 | 51.3 |
| vLLM, no speculation | 35.4 | 35.2 | 34.6 | 35.7 |

TTFT ms, serving-v2, cold (prompt tokens in brackets):

| Engine | short (23) | think (81) | medium (836) | long (3,223) |
| --- | --- | --- | --- | --- |
| **zerv** | **75** | **164** | **706** | **2,483** |
| vLLM | 120 | 188 | 712 | 3,332 |
| llama-server | 160 | 359 | 1,190 | 3,367 |

- zerv's outputs are identical with and without speculation. vLLM gave two different greedy
  outputs across repeats for most cases (its outputs are not reproducible run to run here).
- **Weak spot:** the 836-token TTFT is only 1% ahead of vLLM (706 vs 712 ms). Prefill
  throughput at mid-size prompts is the next single-user target.
