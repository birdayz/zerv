# f16 prefill: wave32 GEMM on f16 X integrated for Q4_0 (block 16b, 2026-09-24)

Question: does the lab kernel k64 ([lab report](2026-09-24-gemm-f16-lab.md)) speed up
f16-mode prefill end to end without changing a single output bit? And where does zerv
now stand against llama-server's default fast path?

Spec: [prefill.md, "f16 GEMM, wave32 kernel with f16 X"](../specs/prefill.md).

## What changed

- **`src/model/gemm_f16x.comp`**: the k64 structure.
  - wave32 with required subgroup size and full subgroups;
  - 2×4 waves of 64×64, tile 128×256, BK 64;
  - Q4_0 dequantized once per workgroup into LDS with the exact `0x6400|q` bit trick;
  - B fragments loaded straight from an f16 copy of X;
  - X's descriptor used before the loop, so it is not reloaded per k-step.
- **Selection** `gemm.f16Kernel`:
  - Q4_0 with M ≥ 4096, K % 64 == 0 and plan rows % 256 == 0 → `gemm_f16x`;
  - other f16 projections (Q4_1, Q5_K, the 128-row plan) → `gemm_f16` (block 14);
  - small shapes stay FP32.
- **Validation** `gemm.validateF16x`. The weight checks are factored out of `validate`
  (`checkA`) and shared.
- **f16 X copies:**
  - `model.comp` built with `F16OUT` gives the `norm_h`, `swiglu_h` and `gate_h`
    producers. They store `float16_t(y)` of the FP32 value they write into the arena
    region `x16` (rows × ffn halves, reused by one input at a time).
  - The runtime uses them only when a consumer in the next GEMM phase runs `gemm_f16x`.
  - The FP32 modules are **byte-identical** to before (`compile_model.py`; the four new
    modules are the only additions).
- **GPU layer:**
  - `Kernel.Options.full_subgroups` (`REQUIRE_FULL_SUBGROUPS`). The device enables
    `computeFullSubgroups` with subgroup size control.
  - The binding constant was regenerated twice, identically, from the pinned registry;
    the ABI fixture now has 56 structs and 78 constants.
  - The kernel cap rose from 64 to 128 (`gpu.max_kernels`): f16 mode now needs 71
    kernels on 4 weight banks, and FP32 needs 55.
  - `gemm.deviceNeeds(precision)` gives the device features for the server and tools.

## Interpretation

- **The GEMM gain carries through end to end, bit-exactly:** −18% prefill GPU time and
  −16% TTFT at 3223 tokens, −14% at 12k.
- **Against llama-server's default fast path** (f16 WMMA with f16 accumulation, less
  precise than zerv's f32 accumulation):
  - zerv f16 is **1.12× faster at 3223 tokens** (it was 1.04× slower) and 1.26× faster
    at 836;
  - **3.6% slower at 12k**. The remaining long-prompt loss is prefill attention: the
    materialized-score FP32 path grows with position (`scores` + `pv` = 264 ms of the
    2.9 s at 3223 tokens). That is block 16a.
- **Precision caveat:** zerv f16 still fails block 14's quality gate 2 on the single
  worst token of long-think; see [f16 prefill](2026-09-24-f16-prefill.md) and design
  question Q1. This change did not alter a bit of it.
- **Next GEMM steps:**
  - Q4_1 (part of ffn_down) and Q5_K (ssm_out, 201 ms, unchanged) on the same
    structure;
  - the 128-row plan;
  - the M = 5120 shapes, which fill 83% of the last round of workgroups on 96 CUs.
