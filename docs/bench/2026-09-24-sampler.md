# Token sampler: component benchmark and the top-k-off path (2026-09-24)

Question: what does sampling one token cost on real logits, per sampling configuration,
and do the fast paths draw exactly what the reference paths draw?
[Spec](../specs/session.md) ("Sampling").

## Setup

- AMD Ryzen 9 3900X; `zig build sampler-bench-build -Doptimize=ReleaseFast -Dcpu=native`.
- `zerv-sampler-bench LOGITS 248320 5` (`bench/sampler.zig`): 257 real next-token FP32
  logits rows (zerv's f32-KV rows of the long-context KV quality run,
  `third_party/kv-quality/long-kl/zerv-f32/logits.bin`, 36k-token prefix + 256
  teacher-forced steps), every row sampled 5 times with the penalty history growing as
  in a generation; round 1 is warmup. Median and p90 µs per sampled token; `checksum` =
  sum of the sampled ids (equal checksums = the same draws).
- Defaults: requests without `top_k` get the artifact's `general.sampling.top_k` (20),
  like llama-server, so the top-k-off rows below need an explicit `top_k: 0`.

## Finding and change

- Before, every configuration without top-k sorted all 248,320 candidates:
  **29 ms per token, 1.5× a decode step**, on top of the GPU work.
- Now (definition in the spec, both paths):
  - with top-k off, top-p's denominator is summed in id order (as llama.cpp's softmax);
  - the fast path sorts only a nucleus prefix found from a quarter-logit mass histogram
    (buckets are strict logit ranges, so the prefix is exactly the start of the full
    sorted order; it grows if the cutoff falls outside it);
  - with no truncation at all, the draw walks the candidates in id order without sorting.
- Draw-for-draw equality with the full-sort reference: `tests/session.zig` "sampler
  nucleus prefix equals the full-sort chain with top-k off" (peaked, flat and
  integer-tail logits; top-p 0.5 / 0.95 / 0.999 / off; min-p; penalties; 24 × 40 draws).
  A mutation that breaks the prefix property makes it fail.
- Seeded outputs of top-k-off requests differ from earlier builds (the summation order
  changed); the distribution is the same. Top-k configurations are unchanged.

## Vectorized exponential (runs 5–6)

The remaining 3.2 ms were 248k scalar f64 `exp` calls. `sampler.expNeg` is the
sampler's own exponential for x ≤ 0: Cody–Waite reduction, degree-13 Taylor polynomial
with fused multiply-adds, exponent-bit scaling, 0 below −708. Scalar and 4-wide calls
return identical values, so the vectorized denominator and draw passes equal the scalar
ones. `tests/session.zig`: worst relative error against `@exp` 2.22e-16 over
[−708, 0] (400k samples), scalar = vector bitwise, exact edges.

| Configuration (top-k off) | fast, before | **fast, after** | reference, after | checksum |
| --- | --- | --- | --- | --- |
| T1, top-p 0.95 | 3,173–3,253 | **1,195–1,243** | 28,459–29,472 | unchanged |
| T1, no truncation | 3,263–3,335 | **1,044–1,122** | 1,033–1,087 | unchanged |
| T1, min-p 0.05 | 179–181 | 180–182 | 26,880–29,242 | unchanged |

Top-k configurations: 58–66 µs (within run-to-run spread of runs 3–4).

## Knob `--sampler-order id|sorted` (added the same day)

The change above alters which token a seed draws (the untruncated draw and top-p's
denominator now run in id order, with `expNeg`). By the work rule, the previous
definition stays selectable: `--sampler-order sorted` (default `id`). See
[session.md](../specs/session.md), "Sampling".

- **Golden:** `tests/fixtures/session/sampler-sorted.json` (sha256
  `2002dc4634a8ffcaeecbe810e36361ef97a81b3d12edfc42312581b19836c23b`): 10 cases
  (`tests/sampler_cases.zig`: no truncation at 4,099 and 65,537 ids, top-p, top-k +
  top-p + min-p, min-p, penalties on tied logits, temperature 0 with a penalty,
  `sampleFrom` over 50 and 300 ids), 24–48 draws each. Generated by running the sampler
  source of commit `3c03b07cfb4acc634b852e5da396abdc02d9cacb`
  (`git show 3c03b07:src/session/sampler.zig > third_party/sampler-head-3c03b07/sampler.zig`,
  sha256 `6e133dba2ea9f8ecb09176d559e462b1fe19c6685d5a7b15baafdd533ad042d5`) with the
  command in `tests/reference/generate_sampler_sorted.zig`. The output is the same in
  Debug and ReleaseFast.
- **Test:** `sorted` reproduces every golden draw, and `id` differs on at least one case.
  Mutation check: routing `sorted` through the new chain makes the test fail (87 pass,
  1 fail).
- **Server (seed 7, temperature 1, 96 tokens, `top_k: 0`, two requests per order, raw
  data in `third_party/sampler-order-e2e/`):** with `top_p: 1` the two orders produce
  different text (sha256 prefixes `d4e0ae2bafd5` for id, `71e3da633e77` for sorted), and
  each order repeats itself exactly. With `top_p: 0.95` both produce the same text.
  Requests that do not send `top_k` use the model default 20 (the top-k path), where
  the two orders agree unless rounding at a cutoff differs.
- **Cost of `sorted`** (runs 7–8, `bench/sampler.zig` now has an `order sorted` path;
  same command and logits as above, [run7](data/2026-09-24-sampler/run7.jsonl),
  [run8](data/2026-09-24-sampler/run8.jsonl)). Median µs per token, run 7. Run 8 was
  noisier throughout (greedy 106 µs against 50) and ranks the same.

  | configuration | id (default) | order sorted | checksums |
  | --- | ---: | ---: | --- |
  | T1, top-k 20, top-p 0.95 (artifact default) | 57 | 1,187 | equal |
  | T0.8, top-k 40, top-p 0.9, min-p 0.05 | 59 | 1,195 | equal |
  | T0.7, top-k 20, penalties | 57 | 1,179 | equal |
  | T1, top-p 0.95, top-k off | 1,121 | 29,929 | equal |
  | T1, min-p 0.05, top-k off | 163 | 34,683 | equal |
  | T1, no truncation | 1,138 | 33,116 | differ |

  On these 257 real rows, `sorted` draws the same tokens as `id` in every truncated
  configuration and different ones without truncation, as expected. Its cost is the old
  one: about 1.1 ms more per token on the default top-k path (partial selection over
  the whole array), and 30–35 ms with top-k off.

## Open

- Top-k-off top-p still costs 1.2 ms per token (ordered summation and bucketing over
  248k values); only requests with an explicit `top_k: 0` pay it.
- Greedy reads 1 MB of logits at about 20 GB/s (49 µs, 0.25% of a step).
