# `--decode-precision f16`: kernel v2 and where WMMA decode tops out (block 18e, part 3) — 2026-09-26

**Question.** Kernel v1 of the f16 batched decode mode ([part 2](2026-09-25-f16-decode-mode.md)) is
flat in the row count but slow: 45 ms at 1 row, 50 ms at 8. Can a restructured kernel with the
same arithmetic make the 8-row step clearly cheaper than FP32's 46 ms, and ideally match FP32's
20 ms at 1 row?

**Answer.**
- **Kernel v2 (`gemm_f16d`, shipped as the mode's kernel):**
  - bitwise equal to v1: gpu-test 15 cases and every split part; model logits hash identical
    in `zerv-batch-check`;
  - 1.3–1.5× faster than v1 per projection;
  - 8-row step 40.9 ms, against 50.6 (v1) and 46.3 (FP32).
- **Q4_1 and Q5_K stay FP32** in the mode (`Options.decode_f16_formats = .q4_0`, the new
  default). Their f16 v1 path is slower than FP32. 8-row step **38.6 ms (207 tok/s at the
  model level)**, still 400/400 batch-invariant within the mode.
- **Not enough for a large margin, and never at 1 row.** Profile and ablations show that
  WMMA decode on this card is bounded near 600–700 GB/s by the matrix instructions' issue
  cost, not by memory.
  - A 16×16×16 WMMA does the full tile of work whether 1 or 16 token columns are real.
  - The FP32 matvec streams ~920 GB/s at 1 row, so f16 can't beat FP32 there.
  - Choosing arithmetic by batch size would break batch invariance, so the mode remains
    an internal, opt-in throughput mode (no CLI).
- **Consequence for the plan:** the large multi-user lever is the exact FP32 multi-row path,
  which runs at ~5.2 TFMA/s of a much higher peak. Its 8-row step could approach the 1-row
  memory time; that is the next work.

## Harness: `zerv-decode-f16-bench` (new, `bench/decode_f16.zig`)

- One projection role (ffn_gate, ffn_down, attn_qkv, attn_q), every layer's copy resident:
  3.2 GB for ffn_gate, far above the 96 MB Infinity Cache.
- One command runs the role over all layers, each layer followed by its split-K reduce and
  barriers, as in the step.
- Kernels: v1, v2, and an experimental SPIR-V with v2's bindings and grid (`--spv`, with
  `--spv-x16 1` for f16-X kernels and `--chunk-align` for research split rules).
- Each kernel's output is checked bitwise against v1.
- **Failed measurements, kept:** the first version kept X, partials and outputs in
  host-visible memory, so every access crossed PCIe. Its numbers (v2 "260 GB/s") are wrong.
  The fix made the buffers device-local, as in the runtime.

Data: [component.jsonl](data/2026-09-26-decode-v2/component.jsonl) (lab variants, 1 and 8 rows),
[component-v1-v2.jsonl](data/2026-09-26-decode-v2/component-v1-v2.jsonl) (1–16 rows), lab SPIR-V

| Role (layers) | v1, 1 row | v2, 1 row | v1, 8 rows | v2, 8 rows | v2, 16 rows |
| --- | --- | --- | --- | --- | --- |
| ffn_gate (64) | 9.55 / 336 | **6.50 / 494** | 9.90 / 324 | **6.63 / 484** | 7.77 / 413 |
| ffn_down, Q4_0 (56) | 8.28 / 339 | **5.75 / 488** | 8.57 / 328 | **6.01 / 467** | 7.84 / 358 |
| attn_qkv (48) | 4.74 / 299 | **3.24 / 437** | 4.80 / 295 | **3.32 / 426** | 3.70 / 383 |
| attn_q (16) | 1.74 / 325 | **1.21 / 467** | 1.70 / 334 | **1.28 / 444** | 1.44 / 394 |

What v2 does:
- one wave32 per 16 × 16 tile, streaming its own 16 rows (no LDS, no workgroup barriers);
- 8 Q4_0 blocks per iteration, loaded before use;
- the lane halves split the dequantization and swap halves (`subgroupShuffleXor`, 16).

## What limits it (ablations, ffn_gate / ffn_down, 1 and 8 rows)

| Variant | GB/s | Finding |
| --- | --- | --- |
| v1 → v2 (first version: 4 blocks, 1 tile per wave) | 336 → 430 | own streaming beats LDS staging |
| 2 or 4 tiles per wave sharing X (`MT`) | no change | X reuse is not the limit |
| LDS-staged coalesced loads (`coal`) | 360–400 | slower |
| no X loads / no dequant / no WMMA (DIAG 1/2/3) | 490 / 470 / 600 | no single part dominates |
| loads only, v2's pattern (`diag5u8`) | 594–627 | the pattern's memory ceiling |
| pure contiguous stream, same grid (`stream`) | 750–795 | the harness's ceiling |
| loads only, 576 B per row, fully coalesced (`srows32u`) | 752–807 | long per-row runs reach the ceiling |
| loads only, lane-owns-row, 576 B (`sown32u`) | 684–759 | also fine, no LDS needed |
| f16 X copy (`xf16`, `u8x16`) | +10–14% | removes 128 conversions per iteration |
| per-lane row segments, 288 B, f16 X (`s16x`, chunks aligned to 512) | **562–577** | best WMMA kernel |

ISA of `s16x`, per 16 blocks per wave (32 WMMAs, 4.6 KB of weights): ~1,500 VALU instructions,
including 128 `v_permlanex16` and 128 selects for the lane-half swap and ~55 per block for
the dequantization.

**Estimate, not a hardware profile:** each 16×16×16 WMMA occupies the SIMD for about 64
clocks. With the VALU work, that is ~3,500 clocks per 4.6 KB, about 630 GB/s over 192 SIMDs
at 2.5 GHz. That matches the plateau of every WMMA variant. The tile computes 16 token columns
however many rows the batch has, so f16 WMMA decode cannot reach the FP32 matvec's ~920 GB/s.

- Wall-clock `decodeBatch` at 8 rows: FP32 48.1 ms, f16 v1 50.6, v2 all formats 40.8, **v2 Q4_0
  only 38.6**.
- Gates: 400/400 bitwise batch-invariant in every configuration. The reference logits hash is
  equal for v1 and v2 with all formats (`a5eb6a0e…`); Q4_0-only is a different arithmetic
  (`3c6d6506…`).
- DeltaNet grows 5× from 1 to 8 rows (0.55 → 2.9 ms), a separate target.

## Changes

- `src/model/gemm_f16d.comp` (new), `gemm.moduleF16d`, `f16dEligible`, `validateF16d`.
- `Options.decode_f16_kernel = .v2 | .v1` and `Options.decode_f16_formats = .q4_0 | .all`.
- `Model.recordBatchProfile` and `decodeBatchProfiled`: phase marks in the batched step.
  The production commands are unchanged: marks are no-ops without a probe.
- `zerv-batch-check`: `f16@v1|@v2[@all]`, a reference logits hash, per-phase profiles for 1 and
  8 rows.
- `zerv-decode-f16-bench` (new). Lab kernels in `bench/gemm_lab/`: `gemm_f16d_{lab,coal,long,wide,seg}.comp`,
  `stream_read.comp`, `stream_rows.comp`.
- `tests/gpu_gemm_f16.zig`: v2 against v1 bitwise. `tests/test_model.py`: the new module and its
  shuffle capability.
- gpu-test 40/40, 0 spill failures.

## Not done

- The f16 X copy (`XF16`, +10–14%) and the 512-aligned split rule (`s16x`) are lab results only.
  They need producer `_h` variants in the batched step.
- No CLI for the mode: it stays internal until it wins at every batch size, which the analysis
  above says it cannot.
