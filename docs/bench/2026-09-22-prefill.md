# Batched FP32 prefill (block 13a) — 2026-09-22

**Question:** does batched FP32 prefill ([spec](../specs/prefill.md)) meet the model
oracle bounds, and how does TTFT compare with llama-server at default precision and
with a fully FP32 llama-server control?

**Result:**
- **Correctness:** every declared gate passes at chunk sizes 1, 13 and 512. Greedy
  output through the server matches libllama.
- **Speed vs. the old path:** TTFT is **7–10× faster** than token-by-token prefill
  (3223-token prompt: 109.3 s → 10.9 s).
- **Speed vs. llama-server:**
  - Against the **fully FP32 llama-server control**, zerv is about even at 836 tokens
    (2.90 s vs 2.93 s), 11% slower at 3223 tokens, and faster at 81 tokens.
  - Against **llama-server at default precision** (Q8_1 integer-dot prompt matmuls),
    zerv is **2.4–3.2× slower** at 836–3223 tokens and **2.7× slower at 23 tokens**.
- **Decode** is unchanged: output hashes and tok/s match the previous zerv run.

zerv is **not** the faster server on prompt processing.

## Setup

Hardware, software and serving parameters:
- Hardware and model: same as the [serving report](2026-09-22-serving.md) — RX 7900 XTX
  (RADV 26.2.3), Ryzen 9 3900X, `Qwen3.8-27B-Q4_0.gguf` (`ede16c7b…671d`).
- Serving: context 8192, one slot, greedy, streaming with usage.
- Workload: [serving-v2.json](../../bench/workloads/serving-v2.json), with prompts of 23, 81,
  836 and 3223 tokens.
- Protocol: one warmup, then 3 repeats per case, with engines run strictly one after
  another. The whole benchmark was run twice.

Engines:
- **zerv**: `zerv --context 8192`. The default `--prefill-chunk 512` gives 128×128
  GEMM tiles and split-K on small-M shapes (target 384 workgroups). The binary is
  `e554ea22…a5b` (`zig build server -Doptimize=ReleaseFast -Dcpu=native`).
- **llama-server FA ub512**, build 10964 (b29c606e): the best configuration from the
  serving report, at default precision. Its prompt matmuls quantize activations to Q8_1.
- **llama-server fully FP32 control**: the same flags plus `-ctk f32 -ctv f32` and
  `GGML_VK_DISABLE_MMVQ=1 GGML_VK_DISABLE_INTEGER_DOT_PRODUCT=1
  GGML_VK_DISABLE_COOPMAT=1 GGML_VK_DISABLE_F16=1`. It uses no activation quantization
  and no FP16 or cooperative-matrix paths.

Exact commands and hashes are in the
[run1 manifest](data/2026-09-22-prefill-serving-run1/manifest.json) and the
[repeat manifest](data/2026-09-22-prefill-serving-repeat/manifest.json).

## Where prefill time goes (per-phase GPU profile)

Tool: `zig build model-profile-build -Doptimize=ReleaseFast -Dcpu=native &&
./zig-out/bin/zerv-model-profile MODEL 8192 512 3223 32`. It prints the sum over layers
of the GPU time between recorded phases (timestamps only in the instrumented command;
production commands carry none).
Raw: [p3223.jsonl](data/2026-09-22-profile-baseline/p3223.jsonl).

- **512-row chunk at p0=0:** 1624 ms total. GEMMs take about 94%:
  - ffn gate+up 702 ms
  - ffn down 379 ms
  - linear-attention input projections 249 ms
  - ssm_out 98 ms
  - attention q/k/v 70 ms
  - attention out 32 ms

  The other phases: DeltaNet scan 56 ms, conv 14 ms, attention scores/softmax/PV
  10.5 ms (at p0=0) rising to 60 ms (at p0=2560).
- **151-row tail chunk:** 830 ms, i.e. 5.5 ms/row vs 3.2 ms/row. The 128-row tile
  rounds it up to 256 rows.
- **Decode step at position 3247:** 45.5 ms, of which fused decode **attention is
  25.3 ms**. This is why decode drops to 25 tok/s at 3.2K (block 13b). The per-token KV
  read at that length is ~0.4 GB, i.e. ~0.5 ms at full bandwidth.

## Interpretation and limits

- Prompt matmuls run at 14–18 TFLOP/s FP32, comparable to llama.cpp's own FP32
  shaders (fully FP32 control). llama's default path is faster because it quantizes
  activations to Q8_1 and uses integer dot products. zerv's default does not do this
  (precision rule). A matched lower-precision zerv mode does not exist.
- **Short prompts are dominated by the tile floor:** ≤128 rows cost the same as 128
  rows (see the ffn_gate rows 1/23/128). The profile of a 23-token chunk
  ([p23.jsonl](data/2026-09-22-profile-baseline/p23.jsonl)) is 431 ms GPU, of which
  GEMM phases are 422 ms. A small-row GEMM variant with the same per-element
  accumulation order would remove most of this.
- Split-K helps small-M shapes. At 256 rows, attn_k went from 1155 µs before split-K
  (implementation log) to 227 µs, and ssm_alpha from 1961 µs to 85 µs (table data).
  ssm_alpha/beta (M=48) remain latency-bound at ~80 µs each.
- The decode regression at long context is the decode attention kernel (one
  workgroup per head, serial over keys), not prefill.

**Correction (2026-09-23).** This report calls llama-server's default prompt path "Q8_1" (integer-dot activations). On this card that is wrong. With `KHR_coopmat` available, ggml converts activations to f16 and uses `matmul_quant_f16_f16acc`: f16 weights and activations with f16 accumulation on WMMA. Q8_1 is used only when cooperative matrices are disabled. The timings above are unaffected. Evidence: [llama precision](2026-09-23-llama-precision.md).
